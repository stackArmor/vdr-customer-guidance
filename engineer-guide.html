Engineering / Kubernetes classification and scanning

Classify your assets.
Scan when useful.

Classification and profile association are required now. The Kubernetes steps below cover the ConfigMap and optional container scanning; non-Kubernetes cloud workloads and resources need vdr-cloud.yaml through the cloud CLI workflow. The optional Trivy VDR plugin can also run in your SDLC to catch high-PAIN vulnerabilities before deployment.

Companion cloud classification

Cover your non-Kubernetes resources.

The customer setup uses two core generation skills. Run generate-k8s-vdr-configmap for Kubernetes workloads and generate-cloud-vdr-config for non-Kubernetes cloud workloads and resources. A Kubernetes-based environment also has cloud infrastructure and managed services that need cloud YAML assignments.

1. Select your cloud scopes and read-only CLI access.

The cloud skill uses aws, az, or gcloud to discover resources and their metadata. Select the AWS accounts / CLI profiles, Azure subscriptions, or GCP projects in scope, confirm the resolved identities, and use credentials with read-only permissions. Azure supports Commercial and US Government clouds; confirm the active cloud and pin the selected subscription for discovery. See the Azure inventory instructions. This covers resources such as VMs, managed databases, and storage, alongside supported cloud infrastructure.

2. Run the cloud generation skill.

Install the VDR agent skills in your approved assistant and invoke generate-cloud-vdr-config. It inventories through the cloud CLI and writes local candidate files under ./vdr-cloud-output/ for your review.

Cloud artifactPurpose
vdr-cloud.yamlProfile assignment rules for non-Kubernetes cloud workloads and resources, plus Class and agency scope.
resource-inventory.jsonThe discovered resources and scopes to compare against assignment coverage.
assignment-coverage.jsonCoverage, confidence, assumptions, and items requiring review.

3. Review and publish the cloud assignments.

Confirm the profiles, multiAgency values, Class, matching rules, and resource coverage. Publish the approved vdr-cloud.yaml to the agreed cloud storage location, such as S3, Azure Blob Storage, or GCS, through your normal change process. Coordinate the storage location and TSW ingestion with your engagement manager or shared Slack channel.

TSW consumes this cloud YAML. The standalone Trivy VDR plugin does not consume it. Applying the Kubernetes ConfigMap covers Kubernetes assignments; the cloud YAML must also be prepared and associated for your non-Kubernetes resources.

Use the two core generation skills for initial customer setup. The corresponding update skills are available for later maintenance. Other published skills are deprecated or intended for stackArmor employees and remain shared for transparency; you can disregard them for this workflow.

01 / Prepare access

Confirm the target before you start.

You can run the classification skills and optional container scans against staging or non-production when that environment is architecturally close to production. Use production-equivalent profiles to get a reasonable view of vulnerability exposure before production deployment. Confirm that assignment rules and identifiers fit the environment where the metadata will be associated.

We recommend a dedicated Kubernetes context, selected with kubectx or kubectl, backed by read-only credentials. For cloud workflows, use a cloud CLI profile with read-only permissions. Confirm the exact target and use the generation skill’s documented access requirements to scope inventory access. Optional scanner setup follows the required classification and profile association below.

CONFIRM YOUR KUBERNETES CONTEXT
kubectl config current-context
↳

Keep staging representative of production. TSW logically separates non-production accounts from production while showing full PAIN scores. Vulnerabilities in a designated non-production TSW account are excluded from TSW’s FedRAMP requirement tracking, reports, and incident automation.

02 / Draft metadata

Generate a reviewable classification.

AI assistance is highly recommended: a manual process that could take days or weeks can produce a first draft in minutes with the agent skills. Review and approval still belong to your team.

Install the VDR agent skills in your approved assistant and run generate-k8s-vdr-configmap. Confirm the target context before inventory. If your team works manually, use the same ConfigMap format and governed classification taxonomy.

ArtifactReview purpose
vdr-fedramp.yamlThe candidate classification ConfigMap: Class, agency scope, and asset profile assignments.
workload-inventory.jsonThe workloads in scope; use it to confirm that the assignment covers the intended environment.
assignment-coverage.jsonAssignment confidence, rationale, assumptions, and items requiring manual review.

The generation skill writes these files under ./vdr-configmap-output/. It uses read-only inventory and does not apply the result.

Understand the three metadata inputs.

InputWhat to confirm
classCertification Class A / B / C / D, matching the applicable FedRAMP status. The skill documents the Ready / Low / Moderate / High correspondence.
multiAgency"true" when compromise could affect multiple agencies; "false" where the impact is limited to one. Record shared-service and dedicated-tenant exceptions.
securityImpactProfileAn independent CR / IR / AR profile encoded as a direct vector, a governed decision trace, or a configured named archetype.

For example, privileged-access.foundation-control.recovery-critical encodes High confidentiality, High integrity, and High availability requirements while preserving the three reasons. A direct vector such as cr-h_ir-m_ar-l records independent levels with evidence kept separately.

The profile is the asset context. It does not itself describe a particular CVE’s exploitability or prove that the vulnerability is internet-reachable.

↳

Review the exact AI workflow. The core Kubernetes generation skill does not retrieve Secret values. Workload specifications and environment metadata may still reveal sensitive system details. Use an approved model service and data-handling configuration.

03 / Review & associate

Associate reviewed profiles with your assets.

  • Confirm that every in-scope workload receives a profile; resolve missing or unknown assignments.
  • Review evidence and assumptions across confidence levels. Start with obvious mismatches and all manual-review items.
  • Confirm Class and the multiAgency default against the actual deployment model, including exceptions.
  • Check existing namespace and workload labels. More-specific labels can override central ConfigMap assignments.
  • Check custom ingress or gateway classes and exposure paths provisioned outside Kubernetes; use the scanner’s documented exposure declarations where needed.
  • Choose availability requirements from the consequence of losing the function. Do not lower AR solely because the workload has replicas or failover.

After review and approval, apply the candidate through your normal change or GitOps process using an approved deployment identity. Keep the skills’ inventory credentials read-only. The following is a customer-operated deployment command; it changes the cluster.

APPLY ONLY AFTER CUSTOMER REVIEW
kubectl apply -f ./vdr-configmap-output/vdr-fedramp.yaml

For a local Kubernetes evaluation without applying the candidate, the plugin also supports --sip-config-map. Follow the current plugin documentation and verify that the local configuration resolves as intended. Coordinate the deployed production assignment surface with stackArmor before rollout.

Optional / Prepare the scanner

Install the container scanner.

Containerized teams can optionally use trivy-plugin-vdr locally or in their SDLC after classification and association. The Kubernetes scanner reference specifies Trivy 0.72.0 or newer. The following commands use Homebrew; use Trivy’s official installation guide for other methods.

LOCAL INSTALLATION
brew install trivy
trivy --version
trivy plugin install github.com/stackArmor/trivy-plugin-vdr
trivy plugin list
trivy vdr --help

With reviewed classification and asset associations in place, confirm the scanner’s read-access requirements, registry authentication, and network access for image retrieval and enrichment sources.

Optional / Scan & SDLC

Preserve the JSON. Explore the report.

Once the approved metadata is available to the scanner, you can run a Kubernetes scan. The scan covers all namespaces here; narrow the scope deliberately to match the environment you intend to inspect.

OPTIONAL KUBERNETES SCAN
trivy vdr k8s --all-namespaces --view resources \
  --output vdr-k8s.json --html-output vdr-k8s.html

Keep vdr-k8s.json as the source artifact. Open vdr-k8s.html locally to inspect and filter the results. Both contain customer scan data and belong in approved storage and transfer channels.

Catch high-PAIN vulnerabilities in your SDLC.

You can integrate trivy-plugin-vdr into the software development lifecycle to inspect containerized workloads before production deployment. Use reviewed, production-equivalent classifications in a representative environment and review high-PAIN findings as part of your deployment decision. Follow the plugin’s platform-specific automation guidance for your environment. This is an optional addition to the required metadata setup.

Review representative findings together.

  • Can you explain the assigned CR / IR / AR profile and where it came from?
  • Does the agency scope match the affected asset’s actual tenant boundary?
  • Do reported exposure and reachability agree with your routing and access architecture?
  • Do the PAIN tier, exploitability context, and remediation timeframe make sense together?
  • Are there failed image scans, partial inventory, or unresolved classifications to correct?
  • Which results would change the team’s remediation order or require a new response process?
!

TSW flags assets using the default H/H/H profile. Missing profiles use conservative High / High / High requirements and the multi-agency fail-safe. Review and correct the profile association. Once the profile is associated with the asset, TSW’s PAIN recalculation uses that profile and adjusts the results accordingly.

  • If you ran an optional scan, the scan JSON, such as vdr-k8s.json, when useful for review.

  • Feedback on confusing classifications, unexpected priorities, missing evidence, and response workflows your team needs.

Maintain coverage

Update when coverage or impact changes.

Classification metadata is generally stable, so there is no fixed schedule for rerunning the skills. Adding a workload or cloud resource is a reason to check coverage; it does not always require another skill run.

  • Existing rule covers the asset: its profile association resolves from that rule. Cloud rules may match tags or names, including supported regex matches. Kubernetes assignments can group workloads by name or namespace. Confirm that the inherited profile fits the asset’s role and impact.
  • No existing rule covers the asset: TSW flags assets using the default H/H/H profile. Add a specific assignment or extend an appropriate rule, then review and deploy the updated metadata.
  • The asset’s role or impact has changed: reassess its profile and agency scope even if an existing rule still matches.

After initial setup, use update-k8s-vdr-configmap for Kubernetes coverage and update-cloud-vdr-config for non-Kubernetes cloud YAML coverage. These skills compare inventory with existing assignments and prepare an additive update while preserving current scores. You can also edit the metadata manually. Use the full generation workflow when a broader reassessment is needed.

After the updated profile is associated with the asset, TSW uses it when PAIN scores are recalculated. Confirm that the corrected assignment is effective and that all in-scope assets are covered.

Platform support & integrations

Choose the right path for your resources.

Supported container platforms

This quick start is for Kubernetes. The plugin has separate Cloud Run, ECS, and Docker Swarm workflows, each with its own access, inventory, and configuration requirements. Follow the platform-specific plugin instructions.

VMs and managed databases remain fully supported.

stackArmor will continue to fully support VM and managed database resources in TSW. The VDR scoring functionality works and will be live in TSW. Scanning for those resources uses commercial off-the-shelf (COTS) products, so we cannot provide a local preview of your system’s VDR scores for them.

Prepare vdr-cloud.yaml for those non-Kubernetes assets as part of readiness. Follow the cloud CLI classification steps above, even when you are also completing the Kubernetes quick start.

Other container technologies: contact stackArmor immediately.

If your container technology is not covered by the workflows here, contact your stackArmor engagement manager or post in our shared Slack channel immediately to agree the scanning and ingestion path.

If you use your own container scanner, its integration must produce JSON in the identical report format as the Trivy VDR plugin, including the same report structure and required fields. Share that output with stackArmor in an agreed cloud storage location so TSW can consume it.

Producing that compatible output can be a substantial engineering effort. You will likely need to adopt the stackArmor scanner for the near future. Coordinate the approach and cloud storage integration with your stackArmor team.
