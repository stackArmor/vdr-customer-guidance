02 / Understand the change

Give each finding
its real context.

VDR means Vulnerability Detection and Response. VER means Vulnerability Evaluation and Reporting. Together, they connect continuous detection with an explanation of impact, exposure, exploitability, and response.

The same vulnerability can have different consequences on different assets. Your classification metadata provides that missing system context.

ASSET CONTEXT

What could compromise affect?

The data and function an asset supports, its confidentiality / integrity / availability requirements, and whether one or several agencies could be affected.

→
EVALUATION

What is the potential impact?

PAIN—Potential Agency Impact—evaluates a vulnerability in the context of the affected asset. Scanner severity is one input to the broader evaluation.

→
RESPONSE

What needs action, and when?

PAIN, exploitability, internet reachability, and Certification Class inform the response priority and applicable remediation timeframe.

↳

The immediate customer action is classification. Have reviewed metadata in place before your VDR integration rolls out. You can prepare it manually or use the agent skills to produce a draft. Either approach must describe your actual assets and follow the supported format.

Our method / Eight evaluation factors

How TSW meets the
evaluation requirements.

TSW brings asset context, vulnerability intelligence, configuration detail, and conservative assumptions together to address the eight factors in FedRAMP VER-EVA-EFA. The rule calls for considering these factors in the context of the cloud service offering.

Each factor informs impact, exposure, exploitation likelihood, or the scope of response. They work together through the method below.

Evaluation factorHow our method addresses it
CriticalityAsset Security Impact Profiles capture independent confidentiality, integrity, and availability requirements (CR / IR / AR). TSW combines them with the vulnerability’s impacts, any agency intended-use ceiling, and affected-agency scope to calculate Potential Agency Impact (PAIN).
ReachabilityAsset accessibility, the CVSS attack vector, and direct or confirmed indirect internet triggers determine whether a vulnerability is internet-reachable (IRV) or non-internet-reachable (NIRV). This considers payloads that reach vulnerable components through other services, including components without a public address. Reviewed environmental evidence can refine the determination.
ExploitabilityTSW evaluates exploitation likelihood using the Exploit Prediction Scoring System (EPSS), CISA Known Exploited Vulnerabilities (KEV) membership, and workload persistence. A lower EPSS threshold for IRV than for NIRV explicitly incorporates detectability into the exploitation-likelihood determination. KEV establishes a Likely Exploitable Vulnerability (LEV); ephemeral workload handling and CVSS chain prerequisites provide additional context.
DetectabilityTSW evaluates detectability through its exposure-based EPSS thresholds: the same EPSS score can produce a different LEV / NLEV determination for IRV and NIRV. This accounts for the greater opportunity to identify and probe internet-reachable software. The method conservatively assumes internet-reachable vulnerabilities can be discovered. How detectability informs likelihood.
PrevalenceTSW tracks vulnerability counts on each component and affected-component counts for each vulnerability or rule. Findings preserve the remediation component needed for a lasting fix, including each container or init-container reference and the Auto Scaling Group that recreates VMs. This identifies spread and the configuration locations still needing action.
PrivilegeAsset classification considers IAM roles, RBAC, service-account authority, credentials, impersonation, and workload privileges when assigning CR / IR / AR. This captures the consequences of compromising the asset’s authority. Chain analysis adds privilege prerequisites and projected capabilities; where evidence is unavailable, the method assumes privilege gain is possible and grants no reduction.
Proximate vulnerabilitiesCWE identifiers and CAPEC-derived capabilities and prerequisites identify chainable entrypoints. An IRV vulnerability may enable exploitation of a downstream NIRV vulnerability through the capabilities gained and the data flow. Supported chains can apply the IRV remediation timeframe downstream; environmental evidence and conservative assumptions remain distinguishable. How entrypoints affect downstream response.
Known threatsCISA KEV, EPSS enrichment, and vulnerability references inform threat evaluation and the likely / non-likely exploitation determination (LEV / NLEV). KEV records identify known exploitation and required action. When an applicable KEV due date precedes the calculated FedRAMP deadline, the earlier date governs.

Criticality, vulnerability impact, and agency scope determine PAIN. PAIN, Certification Class, exploitation likelihood, and internet reachability then select the remediation timeframe. Prevalence and the other contextual factors also guide investigation, grouping, and remediation scope; considering a factor does not require a separate numeric score or a PAIN increase.

Fix every remediation component. This is the configuration component you must update so a fix survives restart, redeployment, or scaling. See the container / init-container and Auto Scaling Group examples.

Confirm who could be affected.

The multiAgency setting records agency scope. It is an architectural decision: a shared service may have a different scope from a dedicated tenant’s workload.

Single agency
multiAgency: false
Compromise is limited to one agency—for example, dedicated tenant infrastructure with an isolated impact boundary.
Multi-agency
multiAgency: true
Compromise of shared infrastructure could affect multiple agencies. This can increase the applicable PAIN tier.

Keep the metadata review practical.

Also confirm your FedRAMP Certification Class and any asset-level exceptions. Review coverage, obvious mismatches, and assumptions flagged for review. Resolve material uncertainty with your stackArmor team as you complete the required assignments.

A profile can use a direct vector such as cr-h_ir-m_ar-l, a governed three-part decision trace, or a configured named archetype. The classification guide explains the taxonomy and examples.

FAQ / Common questions

Frequently asked
questions.

Start here for answers about AI, staging, platform support, and keeping metadata current. For questions about your environment, contact your stackArmor engagement manager or use our shared Slack channel.

Will the existing vulnerability workflow remain available for DoD/DoW workloads?

Yes. stackArmor will keep the existing vulnerability management workflow functional for customers managing DoD/DoW workloads. If a system supports both DoD/DoW and FedRAMP workloads, you may need to manage both the sponsor-required process and the VDR / VER process during the transition and potentially longer.

Ask your DoD/DoW sponsor whether it supports VDR-based evaluation or reporting, whether updated guidance is available, and which existing requirements must continue. Read the DoD/DoW and parallel-workflow guidance.

What should we discuss with our agency before the VDR transition?

Ask your agency contacts how they are preparing for the December 7, 2026 FedRAMP VDR / VER transition, which reports they expect, and how they want changes in identifiers, impact ratings, and remediation dates explained. stackArmor plans to provide a CSV export of VDR results using a familiar POA&M format alongside structured VDR JSON reporting. This would not mean maintaining a separate traditional POA&M process for FedCiv agencies; continued legacy workflow support is for DoD/DoW workloads.

Use the agency coordination guide to prepare the discussion and share agency feedback with your stackArmor team.

Did stackArmor evaluate other VDR solutions, such as Tenable or Wiz?

Yes. We evaluated solutions including Tenable and Wiz. They offered capabilities our previous platform could not accommodate, but incorporating them into our service would have required additional customer costs that we expected to be significant. When we began this work, none of the solutions we evaluated provided the complete VDR implementation our service needed, so custom development would still have been necessary—particularly PAIN calculations using agency, workload, and affected-agency context.

Public documentation did not make clear whether—or how—the tools accounted for protocol handling, curated trusted-source allowlists, inbound versus outbound attack paths, and discovery opportunities. They may consider these conditions; we needed documented reasoning to explain the resulting determinations and corrective action. Read the specific questions behind our transparency approach.

Will stackArmor integrate other vulnerability management technologies?

We are open to evaluating other solutions for TSW. A proposed integration needs a full capability review, documented evidence, and an explainable mapping into PAIN, LEV / NLEV, and IRV / NIRV that addresses all eight evaluation factors. We also review operational fit and customer cost. Support for a specific new product depends on that assessment. Additional integrations would likely require substantial time and engineering effort and could involve additional customer costs.

See the integration criteria, then contact your engagement manager or shared stackArmor Slack channel. Current supported scanner workflows remain available.

How can we understand why TSW considers a vulnerability internet-reachable?

Our method looks at the vulnerable component and its required trigger alongside deployment evidence. Relevant questions include exposed protocols, allowed source addresses, load-balancer behavior, whether the interaction is inbound or outbound, and whether another vulnerability supplies an entrypoint. These facts also help identify the right corrective action.

Read the protocol and attack-path examples, including the RADAR TRACE work being incorporated into TSW and submitted to NIST as proposed NVD enrichment.

Which agent skills do we need to run?

The two initial customer skills are generate-k8s-vdr-configmap for Kubernetes workloads and generate-cloud-vdr-config for non-Kubernetes cloud workloads and resources. Run both when you operate Kubernetes and cloud resources. The cloud skill uses the AWS, Azure, or GCP CLI to collect metadata and produces vdr-cloud.yaml, covering VMs, managed databases, and cloud-native container workloads such as AWS ECS and GCP Cloud Run. The Kubernetes skill uses kubectl and produces the vdr-fedramp.yaml ConfigMap.

Use the corresponding update skills later to refresh coverage. Other published skills are deprecated or intended for stackArmor employees and are shared for transparency. See the two classification paths.

How often do we need to rerun the skills?

There is no fixed schedule. Assignments are generally stable, and existing tag, name, or namespace rules may already cover new assets. Review coverage when resources are added or their role changes. TSW flags assets using default H/H/H so you can correct missing associations; PAIN reflects the updated profile after recalculation. Read the maintenance guidance.

Do we have to use AI?

AI assistance is highly recommended with an approved coding agent. The skills are 100% open source: their instructions are written in plain English, and their helper scripts are available to inspect. Anyone can read exactly what they do. Your team still reviews and approves assignments, and you can prepare the metadata manually.

Will the agent change our environment?

The open-source skills use your active kubectl, gcloud, AWS CLI, or Azure CLI credentials. You retain control of the selected context, profile, and permissions; use read-only inventory access. The generation workflows read system/asset metadata and write local candidate files. Applying a ConfigMap or uploading the cloud YAML is a separate customer action through your change-management process.

You can run the skills against staging or non-production if that environment is architecturally close to production. Review the specific skill’s permissions and scripts before use.

What information does AI-assisted classification use?

Classification covers system/asset metadata only, not federal agency data, application content, or sensitive customer information. The skills are 100% open source, with plain-English instructions and inspectable scripts. They run using your own active CLI credentials, so you control what they can access.

Use an approved coding agent and configuration. Customer information must not be shared with unauthorized third parties. The generation skills do not retrieve Secret values; metadata still requires appropriate handling.

Do we need to run the container scanner?

Kubernetes production readiness includes deploying the plugin in-cluster, confirming the generated ConfigMap is present, and running the latest plugin version against it. Scan output must show metadata association with no default profiles. Local exploratory and SDLC scans remain optional additions. For non-Kubernetes cloud metadata, your preparation is complete once the YAML is uploaded and stackArmor confirms TSW’s cloud identity has read access.

Containerized teams can use trivy-plugin-vdr to preview PAIN scores and can integrate it into the software development lifecycle (SDLC) to catch high-PAIN vulnerabilities before deployment. TSW provides the production finding dispositions, vendor dependencies, mitigation evidence, and response workflows.

Is the Kubernetes ConfigMap safe to deploy?

The ConfigMap contains metadata the scanner reads; it does not change application behavior, networking, or workload settings. Applying it creates or updates that metadata object in Kubernetes. The scanner consumes it read-only. Use your approved in-boundary change-management process for deployment.

The skill fails to run. What should we check first?

Start with the active CLI profile and cloud credentials. Confirm that kubectl, gcloud, AWS CLI, or Azure CLI is authenticated to the intended context, project, account, or subscription and has the documented read-only inventory permissions. An incorrect or unauthenticated profile is a common cause of failure. Check the reported error and the access preparation guidance.

What if the validation output shows coverage gaps?

The skills produce inventory, assignment-coverage, and validation output so you can check coverage across the resource types discovered. If resources were added after the run, use the Kubernetes update skill or cloud update skill. Supply the existing YAML when prompted so the skill can identify and close the gaps. If the environment did not represent production, rerun against a representative environment and verify production coverage.

Resolve reported discovery or validation failures before treating coverage as complete. Review ongoing coverage maintenance.

How does this impact my existing findings, POA&Ms, and due dates?

The transition to risk-based vulnerability management through TSW’s Vulnerability Detection and Response (VDR) capabilities is managed as an adaptive change to the system.

Your baseline scanning methods are not changing. You will continue to use the same methods, such as Nessus vulnerability and database scans and web application scans, in accordance with FedRAMP and RA-5 requirements.

Finding scopes and due dates will change. TSW groups findings differently from the previous GitLab process and determines vulnerability due dates using the Potential Agency Impact Number (PAIN), likelihood of exploitation, and internet reachability of affected components. For the FedRAMP VDR process, findings will be tracked and managed in TSW instead of GitLab. Existing workflows remain available for DoD/DoW workloads.

Because scopes and due dates are changing, the transition will be managed as a one-time reset. TSW will ingest current vulnerabilities and compliance findings, then use security profiles and PAIN, internet reachability (IRV), and likelihood of exploitation (LEV) determinations to assign due dates and manage the findings lifecycle under VDR requirements.

Previous POA&M item counts will not match TSW finding counts because the scopes differ, so comparing the counts is not meaningful. We will be able to demonstrate that previously tracked findings remain tracked and managed in TSW and have not been dropped.

Under the Vulnerability Evaluation and Reporting (VER) consolidated rules, TSW will produce current, accepted, and historical vulnerability exports in the required JSON formats defined at fedramp.gov/schemas. To help agencies adjust to the new reporting, stackArmor also plans to provide a CSV POA&M export using the familiar previous FedRAMP template. The export can be provided to agencies on request and will use the scopes and due dates from the new TSW VDR process. Read the agency transition guide.

Is the HTML report the final production interface?

The HTML report is a local exploration tool. It embeds scan data and lets you filter and review the results. TSW provides the production experience and workflows. Treat both the HTML and JSON as security-sensitive customer artifacts.

Will VMs and managed databases still be supported?

Yes. VM and managed database resources remain fully supported. Their VDR scoring functionality works and will be available in TSW. We use commercial off-the-shelf (COTS) scanning products for those resources, so we cannot offer a local preview of your system’s VDR scores for them.

Do the agent skills cover Docker Swarm?

Docker Swarm is not yet covered by the agent skills. We have a path forward; please contact stackArmor support through your engagement manager or our shared Slack channel for guidance.

What if we use another container technology or our own scanner?

If your container technology is not covered by the Kubernetes, Cloud Run, ECS, or Docker Swarm workflows here, contact your stackArmor engagement manager or post in our shared Slack channel immediately.

To keep using your own container scanner, you must produce JSON in the identical report format as the Trivy VDR plugin and share it with stackArmor in an agreed cloud storage location so we can consume it. That integration can be a substantial lift, so you will likely need to adopt the stackArmor scanner for the near future. Read the integration guidance.

Should we classify a staging environment differently?

No. Make staging representative of production and use the same classification approach so you have a reasonable view of vulnerability exposure before production deployment.

TSW logically separates non-production accounts from production while showing the full PAIN scores. Vulnerabilities in a designated non-production TSW account are excluded from TSW’s FedRAMP requirement tracking, reports, and incident automation.

05 / Keep coverage current

When do we need
to rerun the skills?

There is no fixed rerun schedule. Classification assignments are generally stable. Review coverage when you add a resource or workload, or when an existing asset’s role, data, impact, or agency scope changes.

A new asset may already match an existing assignment rule. In that case, the rule supplies its profile without another skill run.

Already covered? The rule applies.

Cloud rules can assign a profile to resources with matching tags or names, including supported regex name matches. Kubernetes rules can cover workloads by name or across a namespace.

New assets that match those rules receive the existing association. Confirm that the assigned profile fits their actual role and impact; sharing a name pattern or tag alone does not establish that the classification is appropriate.

A gap or changed role? Update the assignment.

If an asset is not covered, TSW flags its default H/H/H profile for review. Update the metadata manually or use update-k8s-vdr-configmap for Kubernetes and update-cloud-vdr-config for cloud YAML coverage. These update skills are for ongoing maintenance after the initial setup.

Once the profile is associated, TSW uses it when PAIN scores are recalculated and adjusts the results accordingly. Reassess an existing assignment when the asset’s security consequences change.
